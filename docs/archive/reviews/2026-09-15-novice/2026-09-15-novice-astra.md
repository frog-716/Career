# Career OS 冷启动体验审查

**结论：我能理解并使用资料、机会和记录，但尚不能顺畅地完成“拿已有职业事实准备一份岗位简历，再登记这次投递”的完整目标。最应优先解决的是简历新增的鼠标操作障碍，以及新简历版本与实际投递记录之间的断点。**

产品已经有值得保留的基础：**资料确认、修订历史、分析前选材、旧结果过期提醒，以及岗位下一步与首页的联动，均在本轮真实操作中成立。** 困难主要发生在跨模块交接和写错之后的恢复。熟悉产品后，我能通过记住各入口继续工作；第一次使用的人则需要自己拼出“哪份内容存在哪里、哪个版本能用于什么”的规则。

本报告不是源码审计，也不是实际 AI 能力评测。**岗位评估只运行了 TestProvider；PDF 没有完成文件内容验收；真实投递没有发生。**

## 1. 审查范围与证据边界

- 日期：2026-09-15。主要交互证据约为页面时间 09:01—09:13。
- 角色：唯一受委派的 Astra/high 冷启动体验审查员。对产品没有预先知识；架构经验仅用于解释观察和提出建议，不用于猜内部实现。
- 入口：仅访问 `http://127.0.0.1:8767/` 及从其页面进入的路径。页面显示“测试空间”。没有访问 8765。
- 环境：主控提供的同构建空白隔离空间，TestProvider。**“与正式站同构建”来自主控的实验控制说明，并非本审查员读取或比较源码得出的结论。**
- 主控独立环境校验：主控报告正式数据 `current`、`revisions`、`records` 三表摘要与审查开始基线一致，8 个构建 artifact 哈希未变。此项与浏览器体验证据分开记录，本审查员未读取正式数据或构建文件复核。
- 方法：真实浏览器 UI 点击、输入、键盘操作、页面快照和截图。只读 DOM 用于确认可见控件、字段和交互状态；没有通过 API、数据库、隐藏状态或产品源码获取业务答案，也没有借此写入业务数据。
- 未读取：项目源码、README、内部产品说明、历史测试、用户既有资料和旧审查结论。没有修改产品、构建或配置。
- 本轮浏览器截图为约 1280×720 的桌面环境；不把单环境观察直接推广为所有浏览器表现。

**虚构场景：**林澄，有 5 年 B2B SaaS 产品经验，正在从栖云软件申请澜桥科技的高级采购产品经理。需要复用审批重构项目，准确表达统计口径与本人贡献，不能把 AI 原型写成生产上线经验。先允许每月出差 3 天，后改为不接受出差，用来检验分析是否仍引用旧条件。姓名、公司、项目、招聘信息、邮箱与所有记录均为测试构造。

我给自己的成功标准是：录入可信事实 → 判断岗位 → 做出并保存岗位简历 → 明确这次机会使用的版本 → 登记投递 → 准备和复盘面试 → 修正事实并再次使用。**截至本轮，投递登记断点未跨越；其余若干环节完成，但不是整条链路全部通过。**

## 3. 优先处理的发现

严重度约定：P1 为核心用户目标受阻；P2 为明显额外操作、误解或长期使用成本；P3 为较低优先级的说明与可发现性问题。这里的优先级是**体验审查判断**，不是生产事故等级。

### N01 · P1：简历新增的鼠标路径无反馈，键盘路径可用

**观察：**在空白编辑器能修改姓名、章节名称并保存。点击项目经历旁的 `+`，以及技能旁的 `+`，均未出现新内容、弹窗或错误说明。依据控件标题重新定位“增加项目经历”，并用原生无障碍点击交叉尝试，结果仍无变化。保存、重新进入后，使用 Enter 激活该控件，出现项目名称、职责、时间和“已增加项目”；同样可以通过 Enter 增加要点。

只读 DOM 当时显示这些工具按钮及父元素的 `pointer-events` 为 `none`。**这是当时渲染状态的线索，不能据此宣布 CSS 根因已确定；本轮也没有验证真实鼠标悬停的完整路径或其他浏览器。**

- **预期：**首次用户以常规鼠标操作即可新增一条可编辑项目，并获得即时反馈。
- **最短复现：**岗位 → 简历 → 编辑当前工作稿 → 点击“增加项目经历”；对照同一控件的 Enter 激活。
- **影响：**从已有职业资料制作简历的主路径看似失效；用户很难想到用键盘试出功能。
- **改进：**让空白章节的新增入口始终清楚可见、可点；核对悬停、焦点、点击命中区域；新增后聚焦首个字段。
- **验收：**在支持的桌面浏览器，首次进入空白工作稿，用鼠标分别新增技能、工作、项目和教育，均只增加一条并聚焦；键盘同样可用；保存重入后内容一致。
- **证据：**[空白编辑器](2026-09-15-novice-assets/03-empty-editor.png)、[鼠标尝试后未新增](2026-09-15-novice-assets/04-add-entry-no-change.png)。后续键盘新增、保存和恢复由本轮 UI 快照核实。

### N02 · P1：新简历版本能关联机会，却无法沿可见入口登记这次投递

**观察：**保存“澜桥采购产品｜事实版 v1（虚构测试）”后，在岗位简历页成功关联。新工作台的“文档与版本”和“方向与机会用途”也显示同一版本。随后点击“查看早期文字草稿与投递记录”，进入“早期记录”：目标岗位正确，正文却为空、版本为 0；“实际投递记录”提示从上方已导出 PDF 的版本登记，上方没有刚保存的新版本。新版本列表和用途列表中也没有发现登记投递入口。

- **预期：**我能直接选择刚用于这个机会的固定版本，登记时间和渠道，不再另建一份文字稿。
- **最短复现：**新编辑器保存版本 → 岗位关联此版本 → 查看早期文字草稿与投递记录 → 检查可登记版本。
- **影响：**“准备 → 使用 → 实际投递”的连续目标受阻；容易把阶段改为“已投递”当作完成，但页面又明确说明阶段不登记实际投递。
- **改进：**在机会关联版本旁提供“登记已发生的投递”，直接引用该固定版本；让新旧版本共享可理解的投递入口，清楚标识来源。
- **验收：**全新空间只使用新编辑器，即可保存版本、关联岗位、登记一次投递并重新打开核对版本/岗位/时间/渠道；随后编辑工作稿，投递引用保持不变；全过程不要求创建早期稿。
- **证据：**[投递入口落到空白早期稿](2026-09-15-novice-assets/05-legacy-submission-gap.png)。

**限定：**这是“本轮从所有已发现的相关 UI 入口无法完成”的结论；不是断言内部没有相应数据模型或接口。

### N03 · P2：研究、面试和工作事项保存后，没有发现修正正文的入口

**观察：**我分别保存研究记录、面试记录、任职事项。详情提供标题、正文、时间和所属岗位/工作卡链接；在来源页、全局面试与复盘、足迹中都未发现编辑或追加更正按钮。Wiki 则有明确“编辑/历史”，形成明显差异。

- **预期：**发现记错事实或需要补充时，能回到原记录修正，保留必要的历史。
- **最短复现：**岗位 → 面试 → 记录面试 → 保存 → 打开记录详情，寻找修正入口；研究和事项做同类检查。
- **影响：**用户可能被迫创建第二条更正记录；后续阅读需要自己判断哪条有效，长期资料容易混乱。
- **改进：**记录详情提供“编辑”或“追加更正”；若必须保留原文，显示更正关系与当前有效内容。
- **验收：**保存含笔误的记录，从原模块和聚合页均能修正；刷新和返回后看到一致的当前内容；原记录不会无提示地变成两个并列事实。
- **证据：**[面试记录详情](2026-09-15-novice-assets/06-interview-no-edit.png)。

### N04 · P2：已整理的职业事实到简历、记录到 Wiki，交接成本由用户承担

**观察：**从岗位进入编辑器后是空白工作稿，没有发现从已确认 Wiki 选材的入口，也没有说明如何将资料用于纸面；我重新手动填写项目。面试页的“相关 Wiki”只是打开该机会的 Wiki 范围，显示“暂无内容”，没有携带刚写的问答或提供整理动作。记录弹窗明确说明记录不会自动成为分析依据，这一点清楚，但没有告诉我如何在需要时让它成为依据。

- **预期：**明确保留人工确认的同时，为“我现在想复用它”提供下一步。
- **最短复现：**确认个人项目 Wiki → 岗位进入空白简历；或保存面试 → 相关 Wiki。
- **影响：**同一事实重复搬运；人需要记住各处是否同步，容易在源资料修正后漏改其他副本。
- **改进：**提供“从 Wiki 选入工作稿”“将本记录整理为待确认内容”，保留来源和确认步骤。若当前不支持，给出一句明确说明和可执行的手工路径。
- **验收：**新用户可将一条项目事实放入简历、将一条面试改进整理为待确认项；每次都能看出来源和确认状态；未确认内容不会自动混入分析。
- **证据：**[空白简历](2026-09-15-novice-assets/03-empty-editor.png)、[已保存面试](2026-09-15-novice-assets/06-interview-no-edit.png)。

### N05 · P2：分析预览让用户承担了不必要的技术阅读和返回成本

**观察：**预览先列出人能理解的来源及版本，这很好；随后展开完整 JSON 资料包，包含 `schemaVersion`、`taskId`、`epoch`、hash、purpose 等字段。720 高视口中，确认按钮不在初始可见范围内。预览后选材和指令变为禁用，页面仍保留“预览本轮资料”按钮，没有发现“返回调整”按钮；关闭重新打开才回到可编辑选择页。

- **预期：**我能核对发送的事实、来源与版本，并方便地补选遗漏项目。
- **最短复现：**分析岗位 → 预览本轮资料 → 尝试修改选材与指令，观察资料包和确认按钮位置。
- **影响：**重要确认被技术字段淹没，漏选项目后需要重新打开对话框；新用户可能只机械确认。
- **改进：**默认展示按来源分组的可读正文与版本，原始 JSON 放入高级详情；提供“返回调整”，保留本轮输入；固定明确的底部操作区。
- **验收：**在 1280×720 下清楚看到当前步骤和下一步；预览后可返回补选项目且原指令保留；再次预览准确反映修改；高级详情仍能审计。
- **证据：**[分析资料预览](2026-09-15-novice-assets/02-analysis-preview.png)。

### N06 · P2：岗位进入简历后，“返回”丢失正在处理的岗位位置

**观察：**从澜桥岗位的简历页进入编辑器，保存后点击“← 返回 Career OS”，落到“今天”。我需要再次选择机会和简历页才能继续关联版本。

- **预期：**返回进入编辑器时的岗位与页签，或明确给出“返回澜桥岗位”的选择。
- **最短复现：**岗位 → 简历 → 编辑当前工作稿 → 返回 Career OS。
- **影响：**用户中断当前任务链，多机会时还要重新辨认目标。首页能找回机会，故未造成数据丢失。
- **改进：**保留来源上下文和返回地址；编辑器显示当前工作稿与岗位之间是否已建立关系。
- **验收：**从机会 A 进入后返回 A 的简历页；从全局工作台进入后返回工作台；刷新或保存不会错误关联到机会 B。

### N07 · P3：首次资料建设需要自己理解多个内容容器

**观察：**我先从首页整理 Wiki，录入完整原文；之后才发现基础资料是另一份独立正文。页面称其为“独立基础资料正本”，并说分析读取最新版；这解释了技术边界，却没有示例说明姓名、目标、项目、约束各放哪里。“公司与方向”又要求建立目标方向，与 Wiki 中的职业目标同时存在。

- **预期：**首次使用能快速判断内容放置位置，而无需自己推导数据分类。
- **最短复现：**空白首页 → 整理 Wiki → 原始资料、待确认、基础资料 → 岗位的公司与方向。
- **影响：**可能重复填写或漏填；我最终在基础资料和目标条目中写了部分重叠信息。
- **改进：**给出简短示例和逐步指引，例如基础信息、目标约束、项目事实；目标方向明确为机会分类，不暗示是另一份个人目标正文。
- **验收：**首次用户面对姓名、出差限制、项目成果和求职方向四条资料，能在页面提示下完成归位，并在分析预览解释它们为何被选入。

## 4. 已验证成立、应保留的设计

**原始资料与当前事实分离是可理解的。**“人工整理、确认前不进入分析”、待确认页、确认后可编辑及历史版本，形成了完整的可见过程。目标从 v1 改到 v2 后，离开再进仍是 v2，历史保留旧文字。[修订历史证据](2026-09-15-novice-assets/01-wiki-history.png)

**资料变化后的过期保护实际生效。**把出差约束更新为 v3 后，旧评估显示“已过期，请重新分析”和“仅供历史查看，不能应用”；再次预览包含目标 v3 的 0 天限制。本轮只验证此场景，未推断所有来源变化都已覆盖。[旧分析过期证据](2026-09-15-novice-assets/07-stale-analysis.png)

**计划和事实的区分写得清楚。**简历关联说明不代表投递；阶段仅作计划标记；投递页说明不会对外发送。这些提示值得保留，但还需补上 N02 中的实际可操作闭环。

**今日行动能连回原机会。**设置“准备 90 秒案例，确认出差上限”和日期后，首页显示该行动；点击可回到机会。排除后首页移除该机会，恢复后面试正文仍在。

**简历历史恢复有实际保护和结果。**恢复前提供放弃当前、先保存当前、取消三个选择；我选择放弃测试修改后，姓名恢复为原值，页面显示已恢复并保存。

**反馈不打断工作。**编辑器和主应用都能提交短反馈并显示已保存；主应用说明只保存输入、选中截图和当前位置。本轮只提交两条精选反馈，其中第二条修正了第一条对键盘可用性的遗漏。没有验证反馈管理端或处理状态。

## 6. 熟练后更值得投入的方向

**先把一份事实贯穿一次真实行动。**最有价值的下一轮验收，不是继续增加入口，而是让一个全新用户用一条已确认项目，完成岗位简历、固定版本引用和一次投递登记，并在面试后修正这条事实。N01、N02、N03 是这条链上的优先阻碍。

**让“内容归属”和“任务推进”同时可见。**从 UI 观察推断，当前很多信息都有自己的保存位置与状态，但跨位置的交接主要靠用户记忆。建议每份成果都能回答四件事：来自哪里、当前是否确认、用于哪个机会、下一步能做什么。此为产品/架构建议，**不是对内部表结构的断言**。

**建立主动选择的经验回流。**面试记录不应自动变成职业事实，但用户可以选中一段回答或反馈，发起“整理为待确认内容”，确认后复用于下一次面试或简历。来源可追溯，比重复复制更有长期价值。

**用可读的变化说明辅助可信分析。**已有版本与过期机制值得继续发展：告诉我“出差限制从 3 天变为 0 天，旧评估需要重做”，比笼统“资料或草稿已变化”更能指导行动。原始请求包可保留给高级审计，但日常确认面向事实和变化。

**能力边界应在目标入口就能理解。**例如从岗位进入简历时解释当前是一份全局工作稿、是否支持 Wiki 选材；面试入口明确当前主要是记录还是提供训练；首次基础资料给示例。这样用户会减少错误期待，也更愿意使用确实可用的部分。
