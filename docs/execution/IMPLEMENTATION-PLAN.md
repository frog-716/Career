## 2. Agent 与 thread 工作方式

### 2.1 默认安排

| 角色 | 模型与强度 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| 主 thread | Luna / High | 读规格、核对边界、分配当前任务、整合、维护 STATUS | 子 agent 写入期间同时修改同一工作树；自行扩大产品范围 |
| 当前实施者 | Luna / High | 完成一个任务的完整前后端链路及测试 | 开额外子 agent；顺手重构无关模块；动生产数据 |
| 独立审查者 | Luna / High | 先读任务合同，再查冻结后的变更、反例和测试 | 修改业务代码；只复述实施者“通过”的结论 |

角色可以复用，不需要为每个模块长期保留一个 agent。机械读取和链接检查可以使用 Luna / Medium；本次语义修改、数据迁移、安全和验收均使用 High。不宣称提高强度能保证正确。

默认顺序：主 thread 分配任务 → 实施者结束写入 → 固定工作树指纹 → 审查者核验 → 主 thread 收口。

“独立审查”指新建审查上下文，只提供任务合同、基线、变更范围与证据位置，不复制实施过程聊天。宿主若会继承指令或上下文，照实记录，不声称实现了真正的零上下文。

### 2.2 模型和权限必须核实

在界面或有效运行配置中确认主 thread 使用 Luna / High。子 agent 也须通过宿主支持的配置及实际元数据确认；提示词里写“你是 Luna”不构成验证。

不能指定或核实子 agent 的 Luna 配置时，不启动它，改由主 thread 串行实施与复核，并标注“缺少独立审查”。不使用其他模型兜底，不修改未知的全局配置，不启用跳过安全审批的模式。

审查者可以在临时目录产生测试输出；这不授予它修改受审源码的权限。审查环境无法运行测试时记录限制，由主 thread 实际运行，但不得把结果写成审查者独立重跑。

### 2.3 并行规则

本轮默认关闭并行写入。可以并行做只读检索或准备反例，但不能对正在变化的代码宣布最终验收通过。

只有主 thread 已验证以下全部条件，才可升级到最多两个实施者：

1. 两个任务没有先后依赖，写入文件集合不重叠。
2. 分别使用独立 worktree、临时数据目录、端口、日志和浏览器 profile。
3. 不共用真实 Keychain 项、后台服务、schema 迁移或会变化的测试数据库。
4. 各自固定同一已验收基线，主 thread 串行整合并重跑集成测试。

以下属于共享关键区：`core.py`、`app.py`、`main.ts`、通用 UI/类型、Gateway、schema/migration、依赖与锁文件、全局文档、STATUS。涉及它们的任务默认串行。把任务叫“前端”和“后端”不能证明它们没有冲突。

## 3. 开工安全边界

### 3.1 本轮授权范围

可做：读取仓库、在独立开发工作树修改代码与测试、使用虚构资料和假供应商、创建临时环境、按依赖锁文件安装开发依赖、构建并进行隔离验收。

未授权：生产数据库写入或迁移、覆盖当前正式源码/dist、重启或终止正式服务、修改真实 Keychain、真实收费模型调用、发布或推送 Git、清空历史数据、重装周备份任务。

本文件不会让正在运行的正式应用立即获得修复。T13 验收与用户另行明确授权之后，才可做生产切换。

### 3.2 原工作树存在未提交修改时

必须记录 HEAD、分支、已暂存/未暂存/未跟踪文件。不得把 `git status` 不干净直接当作错误，也不得 `reset --hard`、`clean`、自动 stash 或 `git add .`。

建立隔离工作树时，不能只从 HEAD 建副本就声称包含最新代码。应：

1. 暂停其他开发线程写入；记录原工作树相关文件 hash。
2. 从 HEAD 创建专用 worktree/分支。名称带本次日期和唯一后缀，避免覆盖旧目录。
3. 用本地二进制 diff 同步当前已跟踪文件的全部修改与删除；临时 patch 文件权限 0600，不打印正文。
4. 逐项审查并复制必要未跟踪源码、测试、配置和文档。排除 `.env`、凭证、数据目录、缓存、依赖目录、日志和未知二进制资料。用户数据不能为了“完整副本”进入开发目录。
5. 对相关源文件逐一核对 hash；缺失内容不得静默丢掉。把复制进来的原有修改记为 baseline，不冒认为本轮产出。
6. 不为方便创建快照提交而把用户其他修改一并提交。原目录保持不变。

若无法可靠隔离，停止写代码并报告具体缺项；仍可继续只读定位。不要在正在提供正式静态资源的目录里直接 build。

### 3.3 测试环境

临时资料目录必须在代码目录外，权限 0700；明确设置 `CAREER_DATA_DIR`。假模型测试使用当前仓库已支持的 `CAREER_AI_PROVIDER=test`，并核实没有数据内的真实 ModelConfig 覆盖它。

**仅设置 test 环境变量不足以保证不出网。** 测试还应注入 MemorySecretStore、假 ModelGateway/HTTP transport，拦截未声明的出站请求；网页搜索也必须模拟。测试进程移除真实凭证环境变量，不显示其值。

禁止把生产数据库复制到测试后继续使用其中的真实模型配置或 secret_ref。测试默认从空库和虚构夹具开始；真实迁移演练需要用户授权后的隔离副本。

启动隔离服务前确认端口空闲；默认候选 18765，被占用则选择另一空闲端口并记录。不要探测后“复用”身份未知的服务。停止时只终止本次自己创建且身份确认的进程。

### 3.4 schema 与迁移规则

公共源码显示 schema v6，但本地实际版本由 T00 只读检查决定，记为 N。不要直接构造生产 Store 来“只读检查”，其初始化可能执行恢复或写入。

改变旧程序不能安全理解的写入合同、索引或数据结构时，使用 N→N+1 的显式迁移与 runtime fence：旧程序拒绝新库，新程序拒绝未迁移旧库。不能只在初始化里 `CREATE IF NOT EXISTS` 然后继续伪装成旧版本。

迁移必须提供 inventory / dry-run / apply / verify 四种可独立验证的阶段，并绑定源 schema、清单 hash 和备份身份。apply 前再次核对源数据未变化。验证失败整体回滚；未知 owner、重复冲突不猜测归属、不删除资料。

禁止用 `cp workspace.sqlite3` 复制正在写入的 SQLite 充当可靠备份。采用已验证的在线备份接口，或在受控停写条件下完整保全数据库及附件。恢复必须在新目录演练，不能覆盖唯一恢复点。

## 4. 已确定的公共实现合同

本节定义各任务必须共用的规则。无需读完整历史聊天后再自行做架构决策。

### 4.1 领域归属

Research 负责 Research 的读取和修改；Interview 只提交经许可的变化；Resume 只读取允许的资料并修改自己的工作稿；ModelGateway 只负责出站，不持有事实写入权。正式修改通过所属领域入口完成。

按需引入轻量模块，避免通用框架：

| 拟新增职责 | 推荐落点 | 第一位消费者 |
|---|---|---|
| Research 唯一读写与兼容规范化 | `src/workbench/research_store.py` | T02 |
| 来源清单、目标绑定与 stale 判断 | `src/workbench/context_manifest.py` | T02，T06 复用 |
| AI 操作登记、并发去重与恢复 | `src/workbench/ai_operations.py` | T03 |
| 表单关闭与未保存状态保护 | `frontend/src/edit-session.ts` | T01 |
| 可提取文字的 PDF 生成 | `src/workbench/resume_pdf.py` | T04 |
| 本地会话验证 | `src/workbench/local_session.py` | T09 |

同等职责已经存在就原位增强，不要求机械创建上述名称。不得让 schema helper 反向依赖前端或 Provider。

### 4.2 Research 唯一身份

逻辑身份固定为 `(kind, canonical_owner_id)`。`kind` 只取 `company_research` 或 `opportunity_research`。Opportunity owner 先经现有 canonical resolver 规范化。

- 已有唯一记录：继续使用其原物理 `id`。旧的下划线、连字符两种前缀都可以被读到。
- 不存在记录：新 ID 使用当前 research 路径的规则 `kind + ':' + digest(owner_id)`。
- 同一规范 owner 发现多份：返回明确的数据冲突，保持资料不变，列出需要人工决定的记录 ID。不得自动选最新、拼正文或删唯一索引。
- 所有消费者按 owner 查询，禁止自己拼物理 ID 读取。
- 两种类别集合先取并集兼容读，保留 `company_business`、`process` 等旧类别及原意义；不要把一个机会中的公司业务信息自动提升为公司级正本。
- 规范来源时保留原 provenance、原条目 ID、内容及确认状态。缺来源标为 unknown。不得凭字段改名创造 verified/fact 状态。
- 只有格式转换无需语义判断的条目才能自动升级。旧缺失条目 ID 可用“档案 ID + 原序号 + 内容 hash”的稳定摘要分配；碰撞停止，重复执行不再分配新 ID。

推荐内部合同：

```python
# 这是拟实现的内部合同，不是可直接运行的现有代码。
get_research(conn, *, kind, owner_id) -> ResearchDocument
apply_research_changes(conn, *, kind, owner_id,
                       expected_revision, changes, provenance) -> ResearchDocument
```

调用者使用同一个传入事务。禁止 helper 偷开第二个写事务或自行 commit。记录唯一性、CAS（版本一致才写入）和 owner 校验必须在实际写入前生效。

### 4.3 来源与提案

每份新提案至少绑定：

```json
{
  "manifest_version": 1,
  "task_type": "research_update",
  "target": {"kind": "opportunity", "id": "opportunity:TEST-A", "company_id": "company:TEST-A"},
  "target_revision": 7,
  "dependencies": [{"kind": "opportunity", "id": "opportunity:TEST-A", "revision": 7, "content_hash": "sha256-placeholder", "purpose": "current_jd"}],
  "policy_version": "career-context-v1"
}
```

示例 ID/hash 仅作结构示意，不进入真实数据。不存在的 Research 档案要记录“预期不存在”，不能与已有 revision=0 的对象混同。

接受：校验目标身份 → 核对当前依赖及撤回状态 → 校验允许字段 → 同一短事务修改对象并更新提案状态。任何一步失败，不允许部分目标已写入。公司与机会目标按当前产品允许的确认分组执行。

拒绝：仍校验请求有权访问该提案，但不要求来源版本仍相同。过期提案可拒绝；已经结束的业务对象仍可清理其待处理建议。

旧提案缺少足够 manifest 时可查看和拒绝，接受返回 `proposal_requires_regeneration`，不伪造依赖、不自动生成替代提案。

stale 判定与提案状态存储不能因抛异常而被事务回滚掉。可以先返回结构化 stale 检查结果再提交状态，或把 stale 作为读取时的派生状态；不能写 `stale` 后立即抛出导致整段 rollback，再声称已持久化。

### 4.4 AI 操作登记

操作唯一键：`(task_type, target_kind, target_id, idempotency_key)`，由数据库唯一约束保证。分开记录 client_intent_hash 与 dispatched_payload_hash：前者来自本次客户端原始指令、选材 ID 和 prepared_id 等稳定输入，用于判断同 key 是否换了请求；后者在第一次执行时绑定来源版本、prepared manifest、模型配置身份与最终请求。重放先比对原 client_intent_hash，再返回原结果；禁止先读取当前来源重算发送指纹，导致资料更新后同一次重试被误判或重新执行。key 本身不参与业务内容 hash。

```text
reserved → dispatching → succeeded
    ↓            ↓
failed       outcome_unknown
```

`dispatching` 必须在发送外部请求前持久化；这一步之后发生断线、进程中断或结果写入失败，无法证明未执行就归入 `outcome_unknown`。

同 key 同输入：先查原操作，返回原状态/建议引用。不要先重新搜索、读 Keychain 或调用模型。同 key 不同输入：409。原来源后来变更可以返回 stale 提案，但不能偷偷再生成。

超时不自动重试。过期、结果清理、进程重启后也不能复用旧 key 发起新付费操作。明确“重新生成”才创建新 key，并提示可能重复计费。

持久化只存无秘密元数据和建议引用。未处理建议正文默认最多保留 7 天；这是本计划的初始工程值。接受后保留正式对象和最小追溯元数据，尤其不长期保存 AI 原始复盘与用户终版两套正文。旧历史记录不在本次自动清理授权内。

去重凭证的轻量 tombstone 不随建议正文过期而删除。无正文时返回 `result_expired` 或已应用对象引用，不重新调用。仅删除本轮新增、已满足策略的派生正文；Raw、冻结材料、用户历史数据不随之删除。

### 4.5 错误和输入保护

沿用现有 API 错误外壳，补稳定错误 code，不全面替换所有响应。最低包括：

| 情况 | HTTP / 语义 | 用户输入 |
|---|---|---|
| 无权限或未配对 | 401/403 | 保留；不得返回业务数据 |
| 目标不存在或不属于该 scope | 404 | 不泄露另一对象内容 |
| 版本、目标、请求 key 冲突 | 409 | 保留本地输入，展示冲突原因 |
| 输入结构或范围不合法 | 422 | 指明字段；不调用模型 |
| 预算超限 | 413 或项目既有 422 | 提供缩小材料的办法，不静默截断 |
| 确定尚未发出且系统繁忙 | 429 | 可显式重试同 key |
| 外部结果未知 | 结构化 `outcome_unknown` | 显示可能已执行，禁止自动重发 |

只有确认服务端成功保存后，才能重置该表单的 dirty 状态。保存中关闭、导航、Esc、遮罩点击都须走统一关闭流程；不能因其他表单保存成功而清除自己的状态。

### T03：AI 操作去重与未知结果

**范围：R03、R14 的并发和重复请求。** 允许修改拟新增 `ai_operations.py`、四条生成路径（Research、Resume、FinalReview、ResearchPatch）、Gateway、相关 API/UI、schema 和测试。旧 analyze 路径要纳入盘点，不能新旧路径各有一个失效的去重方案。

推荐持久化：独立 `ai_operations` 表，含 op_id、task/target、key、request_hash、manifest 引用、state、dispatch_marker、result_ref、error_code、timestamps；对 §4.4 唯一键建数据库唯一约束。不要用会覆盖旧行的普通 UPSERT 夺取执行权。

明确实施顺序：

1. 新请求先检查参数、scope 和已有 operation。同 key 的终态/运行态优先返回，不访问供应商。
2. 在短写事务中原子抢占 operation。竞争失败者重新读结果，不能继续调用。
3. 确定必要上下文，存 manifest；不持写事务等待网络、搜索或 Keychain。
4. 在发送前持久化 dispatch_marker，然后外部执行；成功后先做结构/领域校验，再在短事务写建议及 operation 的结果引用。
5. 结果落库失败也属于可能已付费，不把 operation 当成可自动重发的失败。能修复为保存既有内存结果时不得再调用供应商。
6. 重启发现遗留 dispatching → outcome_unknown；不自动抢占过期 lease 重新发出。未发送阶段的失败可明确标注未调用。
7. 同一次 UI 操作持有稳定 key。重复点击/网络重试复用它；用户明确“重新生成”才创建新 key。
8. 所有生成路径共用一个出站并发额度，初始为 1。繁忙时在未发送前返回 busy，不为等待占住 DB 写锁。不能每创建一个 Gateway 就创建独立额度；单进程共用同一调度器，允许多个进程访问同一数据实例时须用数据库原子槽位等跨进程协调。释放发送槽位不改变旧 operation 的未知结果状态，也不授权重发。
9. 未处理建议按 §4.4 留存，正文清理后保留去重 tombstone。前端能查看既有结果/未知状态，不用“重试”掩盖再次生成。

API 保留现有路径和旧字段，新增状态字段时同步明确类型。运行中可用 202 搭配 operation_id；成功保留当前成功外壳并附 operation_id；相同 key 不同输入为 409。

回归必须包含：

- 假模型每次给不同答案并计数；串行重试调用数=1，两个并发请求调用数=1。
- 去重覆盖搜索及生成整个操作，不能只防止重复写 proposal。
- 同 key 不同输入 409；原配置被删除后，已完成操作仍能返回其结果状态且不读旧 Key。
- 发送后超时、生成后 DB 失败、进程中断、建议正文过期均不会自动再次调用。
- 真实来源改变后返回 stale 或已保存结果状态；不会给同 key 重新生成新内容。
- 并发额度对多个 Gateway 实例有效；繁忙请求不改变正式对象。

完成条件：对所有真实出站调用点均有计数证据。文档只能承诺本地去重和保守重试，不能承诺供应商端绝对恰好一次计费。

### T05：秘密存储、配置更新与目的地绑定

**范围：R07、R08、R09。** 允许修改 `secret_store.py`、`ai_config.py`、`model_gateway.py` 的配置解析、`ai-config-ui.ts`、依赖清单、必要迁移及测试。不可顺手更名 Keychain service 或修改真实条目。

明确实施顺序：

1. 替换 `security ... -w <key>` 的子进程写入。秘密不得进入 argv、环境变量、临时文件、命令输出、日志、异常正文或 DTO。
2. 新增无秘密操作 journal：operation_id、config_id、expected_revision、old_ref、new_ref、phase、timestamps、error_code。new_ref 在系统写入前预分配并记录。
3. 创建/替换：短事务登记意图 → 关闭事务 → Keychain 写新 ref → 短事务再次 CAS 校验配置并切换引用 → 提交 → 清理未被当前配置引用的 old_ref。
4. CAS 失败或数据库失败：原配置/旧 ref 保持可用；新 ref 进入补偿清理。系统拒绝清理时记录 cleanup_pending，不伪造成功。
5. 删除：先短事务取消默认选择并禁用/删除配置，再清理仅属本配置的秘密。其他配置、别的应用 service 一律不可触碰。
6. 重启：根据 journal 与当前引用对照恢复。无法确定系统写入是否完成时，只处理已知 ref；需要系统授权的操作留待用户显式完成，不在启动长事务里弹 Keychain 窗口。
7. DTO 区分 `configured_ref` 与 `secret_status`。状态至少有 not_checked、ready、missing、locked、error。普通读取不逐项取出秘密或触发授权弹窗。
8. 恢复备份后若 ref 无法使用，显示“需重新授权/录入”，不能仅靠 ref 字符串宣告已配置成功。
9. 将 URL 验证抽成保存、临时连接测试、正式调用共用的函数。拒绝 userinfo、query、fragment；拒绝外部 HTTP；本地 HTTP 只允许显式配置的 loopback。

| 同时出站 | 全进程/实例统一 1 个；防止多个 Gateway 各自放行 |
| 自动重试 | 0 次；用户主动动作受原 operation 状态约束 |
| 单次材料 | 最多 50 个来源；超限要求缩减，必要约束不静默截断 |

## 9. 第三阶段：本地运行与恢复

### T09：本地会话与可信启动器

**范围：R10、R15。** 允许修改 `app.py` 安全 middleware、拟新增 `local_session.py`、`scripts/run.py`、`scripts/macos_app.py`、安装脚本、所有敏感客户端请求适配和关联测试。

威胁边界：防止未配对本机客户端和其他系统用户经 HTTP 读写资料/用 Key；不声称能防御已完全控制同一系统账号的恶意进程。继续默认 loopback 监听、Host/Origin/CSP 检查。

本计划采用**一次性本地配对 + 浏览器 sessionStorage 中的短期 Bearer 会话 + 同源本机恢复凭据**，避免依赖只按 host、不按端口隔离的 Cookie。恢复凭据只是高熵 opaque handle：浏览器可持久保存它，服务端只保存其 digest；Bearer 仍只在进程内和 sessionStorage 中有效。sessionStorage/localStorage 都不能防 XSS，因此 CSP、富文本清洗和禁止任意脚本仍是必要条件。

明确实施顺序：

1. 明确匿名路径白名单：静态无用户数据页面、最小健康状态、配对提交。API docs、state、artifact、配置、读写业务和模型接口不得漏出。
2. 启动时为本实例创建随机配对码，至少 128 bit 熵，有效期 5 分钟，一次消费；通过仅文件所有者可读的本地配对文件/受保护 IPC 交付。不能有匿名接口返回配对码。
3. 第一版允许用户通过明确的本地终端/原生提示读取并输入配对码；不要求复杂无感配对。只在用户主动的交互式 TTY 显示，不写日志，不把码放进 URL、argv、环境变量或静态 HTML。
4. 配对成功发放随机会话令牌，至少 256 bit 熵，默认 8 小时有效，服务重启失效；Bearer 保存在页面内存/sessionStorage，以 Authorization header 发送。同时发放只用于本机同源恢复的高熵 opaque handle：前端可放 localStorage，后端只保存 digest，不把 Bearer 或业务资料放入持久化存储。
5. 新独立浏览器标签页/编辑器若没有会话，先尝试同源恢复凭据；没有恢复凭据时再向已有的同源 Career 标签页请求一次性内存会话转交。转交只通过 `BroadcastChannel` 传递现有 Bearer，绝不写入 URL、日志或跨源 Cookie。恢复凭据和内存转交都失败时，才明确请求重新配对；不能通过未鉴权接口偷取令牌或绕过首次配对。
6. 文件下载通过鉴权 fetch 再创建本地 Blob URL，或同等不泄露 token 的方式；不得为方便下载把 bearer 放 query。退出同时撤销服务端恢复凭据并清掉 sessionStorage/localStorage，保留用户未保存输入。
7. 保留 Origin/Host 和请求类型校验；生产配置不允许 testserver。配对有失败次数与短期速率限制，缺少 Origin 的普通本机请求仍须有效会话。
8. `/healthz` 区分匿名最小健康信息和经授权的诊断信息。后者包含 build_id、schema、data_instance_id、startup_instance_id、静态资源 build_id；不返回原数据目录或秘密。
9. 每个运行数据实例维护受保护身份、PID、进程启动时间与单实例锁。服务是否可复用必须同时验证应用身份、数据实例和兼容构建。
10. stop 不依赖 PID 数字单独 kill。先校验 PID + 启动时间 + 本实例凭据，优先经已认证本机控制路径优雅退出；无法确认则报告未知进程，绝不猜测终止。
11. 新后端对应前端资源带同一 build_id；不匹配提示重载/正确重启，不把任意 app_version 当就绪。
12. 连续双击和两个启动器并发必须由 OS 级单实例锁协调；健康检查不能通过读取整个 `/api/state` 来判断。

回归必须包含：未配对本地 HTTP、错误 Origin/Host、过期令牌、配对码重放、匿名 artifact/API docs 均被拒绝；合法主页面/编辑器/下载/退出可用；服务重启后恢复凭据可获取新的内存会话；不同端口服务收不到此会话令牌或恢复凭据。

真实 Mac 隔离验收：冷启动、连续双击、端口被无关服务占用、旧构建、PID 重用、启动失败、延迟退出、陈旧静态资源。只操作本次测试进程，不停止正式服务。不能把 IAB 测试记录成 Chrome 的独立验收。

完成条件：访问与进程身份边界都通过；若仅 mock 测试通过，标记 `PLATFORM_VERIFICATION_REQUIRED`，禁止宣告上线就绪。

6. 缩短写锁前，先让已发布附件内容和路径不可变，并建立覆盖新增/移动/恢复/清理的附件生命周期锁。必须统一锁顺序：所有相关路径先拿附件生命周期锁，再拿数据库写锁；禁止写入方持 DB 锁等待附件锁、备份方持附件锁等待 DB 锁的反向顺序。现有 artifact/recovery 调用链要一起调整并补死锁反例测试。
7. 推荐流程：持附件生命周期锁 → 用同一已固定的 SQLite 读取快照生成数据库备份与对应附件清单 → 结束该读事务及任何短时写保留 → 复制已列不可变附件并核验 → 释放生命周期锁。不能先取当前清单、再独立备份已经变化的数据库；SQLite 备份 API 的连接与事务方式先用真实并发测试验证，不能在同一连接持写事务调用备份而导致卡死。所有会改动已列附件的路径必须配合该锁。
8. 若不能证明所有附件移动/清理路径受控，保留当前锁并标记性能问题未解决；不能直接删锁制造撕裂快照。WAL 不单独构成修复。
9. 状态记录 last_success_at、last_restore_verified_at、last_error、recovery_point_age。周任务 loaded 与 dry-run 只表示配置，不表示已有备份。
10. 恢复始终到新目录，核对 schema、业务对象、冻结材料、附件 hash。Key 不随备份导出，恢复后模型可能需重新授权，按 T05 显示。

回归必须包含：同周完整/破损目录、孤儿、缺附件、超长文件名/危险路径、磁盘满、复制中断、manifest 篡改、重复执行、恢复到新目录。只读恢复检查不得触发生产 Store 初始化。

压力测试使用虚构 1000 个附件并发人工保存，记录锁时长和 P95 保存延迟。比较同机无备份基线；初始目标为保存 P95 增量不超过 500 ms，属于待测工程预算，超出如实报告。

完成条件：至少一份隔离备份真实恢复并读回完整业务链；完整与不完整恢复点清楚区分。未授权生产恢复不影响完成隔离实现，但不得声称实际生产灾备已经验证。

```text
生产：未改 / 待授权 / 已验证切换
```

日志输出遵循：`command + exit code + short summary`。成功日志不要全量灌入上下文；失败再读取必要局部。日志只含虚构数据或脱敏信息，外部错误正文不能带秘密。

审查者必须报告：严重问题、复现步骤、路径/符号、证据、遗漏测试。仅有意见没有可验证条件时标记推断。主 thread 不得用实施者的自述推翻有复现证据的审查结果。

### 13.3 什么时候停止，什么时候继续

立即暂停相关写入：

- 源数据 owner/冲突无法可靠判断，迁移可能丢数据。
- 测试/命令实际指向生产目录、真实 Keychain 或未授权收费服务。
- 不可恢复操作缺少经过验证的恢复点。
- 当前目标规范与本计划存在真实语义冲突。
- 准备切换正式应用但用户没有明确授权。

普通文件名变更、测试路径不同、局部函数重构可在保持合同前提下自主适配，写明实际映射。不得因为目录名和本计划不同就停工，也不得用目录不同当理由偷偷扩大设计。

一个任务被阻断，依赖它的任务暂停；没有依赖且授权范围内的任务可以继续。例如真实 Mac 验证暂缺不妨碍完成其他纯代码测试，但会阻止最终平台通过/生产切换。

发现疑似真实秘密时不输出内容；暂停公开传播，记录脱敏定位，并说明撤销/轮换需要用户处理。不能仅删除文件就宣告消除了历史泄漏。

### 13.4 切换 thread 的条件

到完整阶段收口、角色目标改变、上下文开始混淆事实与旧方案时换 thread。无需按固定消息条数切换。

切换前由主 thread 把基线、隔离目录、已验任务、未提交文件、阻断项、下一动作写进 STATUS；新 thread 读取当前源文件和 STATUS，不依赖复制旧聊天。未提交内容必须留在已记录工作树，不能新开一个只包含旧 HEAD 的副本。

## 14. Subagent 可复制模板

### 14.1 实施者模板

```text

任务：[Txx + 标题]

自动提交推送、改写用户原有未提交内容、顺手重做产品。

```

### 14.2 独立审查者模板

```text
只使用经宿主实际确认的 Luna / High。你是独立审查者，不修改受审源码，不开子 agent。

任务：[Txx]
冻结工作树：[目录 + HEAD + diff/文件指纹]

重点尝试证明：问题仍可复现、旧资料丢失/串 owner、旧路径可绕过、
模型重复调用、过期建议写错目标、并发覆盖、输入丢失、测试只验证表面结果。
测试只能使用虚构资料、假供应商和临时输出；无平台权限就标明未验。

逐项返回：ACCEPT / CHANGES_REQUIRED / UNVERIFIED，
附路径/符号、触发条件、实际证据与影响范围。

不把 mock/类型检查等同真实浏览器、Keychain、PDF 或备份恢复通过。
```

### 14.3 主 thread 整合约定

主 thread 只基于实际证据验收；子 agent 报完成仍需检查文件范围、差异与测试。共享接口变化后跑集成。修复审查发现仍由实施者做，审查者继续保持只读角色。

当前环境只有主 thread 可用时，按同样任务卡串行完成，并明确缺少独立审查。不要因此调用其他模型或假称另一个 agent 已验收。
