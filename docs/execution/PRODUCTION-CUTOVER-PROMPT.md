不读取、覆盖或删除现有 Career Key。不能为测试拒绝/锁定而锁住整个用户登录 Keychain；需要系统交互时让用户执行针对测试项的选择，做不到就记未验。秘密扫描使用假标记，不打印值。LOCAL_ONLY 下允许本项仍未授权，但必须证明生产相关入口和后台操作关闭。

真实 Provider 默认不调用。AI_ENABLED 另行提交具体目的地、Provider、模型、虚构发送内容、最大调用次数、最大 token/预算和绝不自动重试规则。费用上限不明或未批准时不调用。只发送批准的虚构内容，不读取真实简历/资料作为 smoke 数据。真实搜索如涉及第三方访问也须单列。

## 5. 阶段 3：授权后的正式切换

按照已冻结计划依次执行，每一步写脱敏检查点，失败进入第 6 节。不要运行一条覆盖所有动作、失败后无法辨认进度的脚本。

### 3.1 最终前置检查与停写

- 重新核验授权绑定的源码、主项目差异、环境、目的地、模式和脚本 hash。发生未批准变更立即停。
- 用户保存并停止使用；暂停其他开发线程。核实本应用写入进程和定时作业，按原状态记录并暂缓写入。
- 停止经验证的旧 Career，等待退出并确认端口释放。PID、命令名或占端口其中一项都不足以单独确定身份；身份不明不得杀进程。
- 确认没有未知写入者。确保旧窗口无法继续提交数据，避免旧版与新版同时使用同一资料。

### 3.2 创建最终一致恢复点

- 保全当前主项目有效源码、必要未跟踪文件、静态资源、App 与原任务配置；记录旧环境原路径和可运行检查。
- 创建停写后的最新数据与附件完整备份，验证 healthy/complete。
- 恢复到新目录，按已经演练的迁移执行并校验冻结资料及所有关键关系。
- 实际数据与演练样本出现新冲突或缺失时停止；不得沿用旧演练副本覆盖新增数据。

### 3.3 整合代码并切换运行组合

- 只整合批准清单中的修改。保留用户其他工作和无关未跟踪资料；不把 `.venv`、node_modules、runtime、真实数据、备份或秘密复制入 Git。
- 本地提交如在授权清单内，只提交列明文件；不 force、不 push、不改写已有历史。整合后的有效源码指纹必须与验收发布对象一致。
- 使用固定新 Python 环境和已验证依赖，构建最终主项目静态资源；核实构建产物与源代码匹配。
- 保留旧 App 的可恢复副本，生成指向主项目/批准发布位置与固定新环境的正式 App。禁止正式启动器仍指向 `/tmp` 或本轮 Worktree。
- 按已验证方式切换到迁移后的完整数据集。原数据和备份保留；只可在同一文件系统、无打开连接且前置条件满足时使用原子目录替换。项目要求固定数据路径时，使用已演练的目录保全/替换流程，不能临场重设计目录体系。
- 原每周一任务只更新已批准的解释器/代码/数据路径；保持原 label、周期和保留策略，不创建第二套周期任务。保存旧 plist 与加载状态以便恢复。
- 启动新版。默认仍处维护/禁止正常业务写入状态；AI 开关严格遵守发布模式，生产不启用假 Provider。

### 3.4 正式后置检查，默认只读

这里“只读”指不新增或更改用户业务事实；必要的启动、会话和迁移元数据写入须已列入批准计划。未实现可靠写入隔离时，先保持服务仅供受控检查，不把正常业务入口开放给用户。

1. 核实实际 PID/启动时间、监听端口、解释器、import 路径、前后端身份、schema、数据实例与批准 release 一致。相同的历史 build 文案不足以证明相同源码，还要核对实际生效文件/产物指纹。
2. 真实正式 App 的重复打开、旧 build 拒绝、会话配对/重配对/退出和 Chrome 页面访问符合验证结果；不复用旧会话、不泄露 token。
3. 只读确认机会、Wiki、任职、面试、简历版本及附件可读取；旧投递 PDF hash 与恢复点一致。
4. PDF 导出、生成版本或点击按钮可能写 artifact/run。未经额外批准，不把这些动作伪装成“只读 smoke”。用户链写入测试继续使用隔离 fixture；生产写入验收需用户指定对象和动作。
5. 确认所有启动/备份入口使用新固定环境，离开 Worktree、关闭终端后仍可通过正式 App 工作。
6. 运行全量测试和假供应商测试时，显式使用隔离目录并屏蔽生产配置，不能继承正式 `CAREER_DATA_DIR`。重新验证从干净依赖环境可复现；npm extraneous 条目不作为成功依赖来源。
7. 重新执行质量门禁与 audit，保留 warning、skip、漏洞例外和未验项，不把汇总 exit 0 当作所有外部检查通过。

完成后状态为“已切换，等待用户人工确认”，不得提前写 `ACCEPTED` 或宣称全部交付。

## 6. 失败与回滚规则

回滚能力必须在阶段 2 演练，阶段 3 的有限自动回滚必须包含在用户授权中。

### A. 尚未发生新增业务写入

满足以下全部条件才自动回滚：旧完整恢复点有效、旧源码/App/解释器/任务配置可恢复、新服务可可信停止、没有未知外部副作用。

1. 停止并确认新服务及本应用写入者退出。
2. 保留失败的新数据、日志、迁移证据和目录；不删除现场。
3. 按批准计划恢复旧的完整运行组合。旧代码只打开匹配的旧完整数据集，不打开已迁移新库。
4. 恢复原周任务配置和原有加载状态；核验旧服务身份和只读数据可用。
5. 记录 `ROLLED_BACK` 及实际验证结果并停止；不自动再试第二轮上线。

### B. 已经发生或无法排除新增业务写入

禁止直接用旧备份覆盖。先停止进一步写入，保全当前数据库和附件，列出新增/变更范围；优先评估前向修复或可验证的数据保留方案，再申请用户批准。

迁移、会话与诊断元数据需和用户业务写入区分；无法证明没有业务写入时按 B 处理。新模型调用的潜在费用与外部副作用不能靠回滚数据库撤销。

### C. 回滚前提缺失

保持安全停机或受控只读状态，明确告诉用户旧版是否已经恢复。禁止为了恢复页面可用而连接未知数据库、降低鉴权或丢弃新数据。

恢复生产源码时仅恢复批准清单和本轮变更；执行期间出现其他用户新增文件时保留并报告，不强制整目录覆盖。
