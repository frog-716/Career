# Career 独立 Fresh-Eyes UX 盲审

审查日期：2026-09-27。审查入口仅为 http://127.0.0.1:8772/ 。全程通过 mcp__cua_repl 操作真实 UI；未读源码、设计文档、数据库或网络响应，未访问正式 8765。只在 UI 创建虚构资料；本报告是唯一写入的文件。

## 结论

能独立走通「个人项目 → 原始资料 → AI 建议 → 查看来源 → 接受 → 当前理解 → 不再有效」，也能创建任职、人物、关联项目、机会及独立简历稿。最明显的阻塞是：新建面试成功后，两个进入面试的入口都显示 Not Found。最影响信任的是：项目资料出现在任职和人物的“自己的原始资料”区域，以及简历已经创建保存、机会页却仍说没有准备简历。AI 建议可在关闭和刷新后找回，这是实际走通的优点；但进行中状态不清楚。

没有确认到 P0。以下 P1 指核心任务受阻或事实/归属反馈容易误导；P2 指明显的理解和寻找成本。此处不推断任何代码根因。

## 虚构样本及关键顺序

1. 创建个人项目“星河读书助手（虚构）”，不关联任职。说明：个人业余项目，我负责访谈、原型和上线；10名测试者。
2. 在该项目“添加资料”，保存“首轮用户访谈（虚构）”。正文提到小样本检索由90秒降至40秒、尚未验证长期效果、合作人林晓负责视觉。
3. 后来创建任职“云帆科技（虚构） / 产品经理”，尚未给任职直接添加任何资料。
4. 在任职中创建人物“林晓（虚构） / 视觉设计师”，尚未给人物直接添加资料。
5. 在任职中“关联已有项目”选择星河读书助手。保存后的任职“资料”区立刻出现“首轮用户访谈（虚构）”，说明仍是“只显示这个对象自己的原始资料”。
6. 在任职人物行点击“查看”。人物展开块写“关联项目：还没有关联项目”，但其“资料”区也已出现同一篇“首轮用户访谈（虚构）”，说明同样是“只显示这个对象自己的原始资料”。此时还没有做人物到项目的关联。
7. 随后才从任职打开项目，点“关联人物”，选林晓，输入“项目内角色：试点视觉负责人”。
8. 创建机会“北辰阅读（虚构） / 产品经理”，填写虚构 JD。创建该机会的独立简历工作稿，在简历添加一个项目占位并保存草稿。回机会仍显示“还没有为这个机会准备简历”。
9. 登记虚构不使用简历的投递，再创建“第一轮产品面试（虚构演练）”，排期留空。机会页面成功进入面试阶段；“准备这一轮”和“打开本轮”分别返回相同错误。

## Top 10：证据、误解原因、最小修复

### 1. P1 — 新建面试显示成功，进入本轮却不可用

证据：记录投递→确认“第一轮产品面试（虚构演练）”后，机会阶段变“面试”，轮次显示“时间待定 · 待排期”；点击“准备这一轮”出现“面试不可用 / Not Found / 无法读取该轮次”。关闭后换“打开本轮”，相同结果。主 Agent 说没有已知隔离限制，根因未查。

误解：我会认为刚才保存成功的是一个能继续工作的面试，而不是只能展示的记录。三个入口没有一个恢复建议。

最小修复：使新建轮次与打开轮次的路径一致；失败时明确“轮次仍保留/当前无法加载”的事实，提供重试与返回机会。此项首先是功能阻塞，不能只换文案。

### 2. P1 — “只显示自己的原始资料”与实际对象归属冲突

证据：上文关键顺序第5、6步。项目原文“首轮用户访谈（虚构）”在关联项目后出现在任职自身资料区，人物尚未关联项目时也出现；人物同时写“还没有关联项目”。任职和人物均未自行添加过原文。

误解：我无法判断这篇资料被移动、复制、继承，还是已经作为人物资料使用；这会直接影响我对后续 AI 读取范围的信任。不能仅凭 UI 判断后台真的串数据，但 UI 的承诺与呈现已经矛盾。

最小修复：核对范围取数；若展示关联资料属于预期，就给资料行标明“来自项目：星河读书助手”，并调整“自己的”说明；若不是预期，修正展示范围。关联资料与直接资料应看得出区别。

### 3. P1 — AI 处理中只有按钮灰化，离开后没有任务状态

证据：点击“让 AI 整理”，人为25秒处理期间仅该按钮 disabled，按钮文字不变；关闭后项目页仍显示普通“整理到 Wiki”，没有进行中标记。截图可见整个预览原样、按钮变灰、取消和关闭都在。

误解：无法分辨“没点击上/按钮禁用/正在工作”，也不知道关闭是否取消。若耗时更长，容易重复发起。此次没有做重复请求，不能说已经产生重复结果。

最小修复：按钮改为“正在整理…”，提示可关闭及结果归处；资料行同步显示“正在整理”；关闭按钮与取消请求如含义不同，明确区分。

### 4. P1 — 简历已创建并保存，机会仍说没有准备简历

证据：机会中“编辑简历”→空白创建独立工作稿→简历选择器明确“北辰阅读（虚构） · 产品经理”，初始“已保存 · 本机会独立稿”；添加项目占位后“未保存”，点保存草稿变“已保存”。回机会页仍显示“还没有为这个机会准备简历”。

误解：像是草稿没保存或丢了；也不知道要额外保存正式版本才算准备。可能系统想表达“没有正式版本”，但当前文案没有这层意思。

最小修复：机会明确区分“已有工作稿，尚未保存投递版本”与“尚无简历”；提供继续编辑。保存草稿与保存版本旁用短句解释结果，不只放悬停帮助。

### 5. P1 — 两套 Wiki/原始资料界面让用户不知道该在哪里积累

证据：新 Wiki 已有星河项目原文与不再有效知识；右上点“原求职资料”，显示“原始资料/待确认/已确认 Wiki/基础资料”，默认“全部范围”仍“暂无内容”。返回按钮又叫“返回长期 Wiki”。

误解：“原求职资料”可能被理解成“原始求职资料”，不一定知道“原”是旧版。用户在一个 Career 中面对两套类似承诺、不同内容，没法形成唯一保存位置的直觉。

最小修复：入口明确写“旧版求职资料（历史）”，解释用途与新增应去哪里；将仍需维护的基础资料提供清晰直接入口。避免用另一个 Wiki 名称要求用户理解迁移历史。

### 6. P2 — 首屏默认“全部知识”导致两个主要按钮都不可用，长期认知也藏在筛选里

证据：全新打开落在 Wiki；“添加原始资料”和“写入 Wiki”均 disabled；页面远处灰字“先选一个范围，再写入一条知识”。范围下拉里才有个人职业资料与长期认知。

误解：第一眼像还没配置或没权限。用户必须先学习系统按范围归档的方式，才知道如何开始。长期认知看起来是筛选分类，实际进去是另一种跨经历工作流。

最小修复：空态提供可点击“添加第一份资料”，在动作中选保存位置；把“整理长期认知”作为可见入口或说明其前置条件。禁用原因贴近按钮。

### 7. P2 — 人物展开后多组同名区域削弱操作对象

证据：任职本体有当前理解、人物、关联项目、资料；点人物查看后，在同页插入另一个大卡，内有当前理解、关联项目、资料，然后页面下方又继续任职的关联项目、资料。截图中原人物列表与展开人物卡同时占据大块首屏。

误解：长页面滚动后很容易忘记“添加资料”是给人物还是任职；标题重复，角色位置相同但作用对象不同。尤其资料还出现同一篇时更难分辨。

最小修复：人物详情使用带姓名固定标题的独立抽屉/区域；按钮写“为林晓添加资料”或在资料标题中注明人物。任职与人物边界用明确的视觉层级。

### 8. P2 — 面试首次入口像功能入口，实际只是筛选；空态没有推进指引

证据：点机会列表“面试”，已有机会消失且提示“这里还没有机会 / 添加公司、岗位和 JD，即可开始”；回详情点击阶段条“面试”无变化。直到主动尝试记录投递后，才出现“确认真实面试”。

误解：以为要在面试页再创建一次机会，或阶段条是可跳转的步骤。真实面试先确认的规则合理，但入口隐藏而空态指向重新建机会。

最小修复：面试筛选空态写“还没有进入面试阶段的机会”，给“查看全部机会”；详情阶段条标为进度，当前主任务里说明如何登记已获得的面试。

### 9. P2 — AI 完成通知缺少资料名和直达入口

证据：在简历工作台操作时出现“建议已保存，可以逐条处理；关闭后可从这份资料继续。”实际来自先前项目整理。没有显示“星河读书助手/首轮用户访谈”，也没有“查看建议”。

误解：简历页也有 AI 优化按钮，我会短暂以为这条通知与当前简历有关。“这份资料”在当前页面没有指代对象。

最小修复：通知写“首轮用户访谈的1条 Wiki 建议已就绪”，附“查看建议”；离开通知后可在对应资料行继续的现有机制应保留。

### 10. P2 — 历史能找回，但缺少变化语境

证据：接受后点知识“历史”，弹窗“Wiki 修订历史”只展示事实状态、全文、“手工原文 · ”及查看来源；没有清楚可读的更新时间和发生了哪种操作。后来“不再有效”折叠区与 Wiki 全部状态均可找到内容。

误解：能看见旧内容，但不容易判断何时改过、为什么失效；“在 Wiki 查看历史”又实际打开汇总列表，与单条修订历史含义不完全相同。

最小修复：每条历史显示时间、操作（新增/修改/标记失效/恢复）与来源；两个入口分别叫“查看全部知识（含失效）”和“修订记录”。

## 页面主要任务与视觉判断

| 页面 | 我理解到的主要任务 | 视觉和文案判断 |
|---|---|---|
| 机会列表/详情 | 管理一个岗位的下一步行动 | 详情“现在该做什么”最清楚，有唯一工作方向；列表“机会管线”和混合英文词增加门槛。面试三个按钮“准备这一轮/开始模拟/打开本轮”的范围重叠，需要点开才能判断。 |
| 简历工作台 | 编辑纸面简历并保存/投递 | A4纸面直观；工具栏同时有草稿、AI、版本、PDF、投递，当前主要动作不够集中。保存状态能即时反映未保存/已保存是优点。默认“缩放200%”没有易见调整入口，本次未寻找更多菜单，不能断言不存在。 |
| Wiki | 查当前认知、追溯来源 | 空库两侧空白占比大，按钮禁用降低可行动性；有内容后的状态和来源明确。已确认事实/观察/待验证判断基本能理解，但“对象”“范围”仍偏系统语言。 |
| 任职 | 维护一段工作的经历、人和项目 | 创建入口清楚，后续信息区平铺，难判断“今天该记录什么”；当前进展在人物和资料之后，人物展开进一步把它推远。 |
| 项目 | 放项目资料并形成可引用认识 | 项目说明→当前理解→资料关系可以逐渐理解；一开始“写入 Wiki”比“添加资料”视觉更强，可能让新用户先去手写总结。历史工作记录还使用“事件/成果/证据”，与资料/Wiki形成另一组未解释概念。 |
| 长期认知 | 跨经历整理自己的工作模式 | 文案比入口清晰；“不是人格标签或分数”帮助理解边界。缺资料时给出具体两段经历条件，很好，但缺直接“去补 Wiki”入口。 |

## 值得保留的部分

- 项目可以独立存在，创建表单和成功提示都明确，不迫使先建任职。
- 添加原始资料时明确保存对象；保存成功提示具体。原文与 Wiki 的区别经过一次操作能理解。
- AI 发送前展示所读新资料、对象和已有 Wiki；来源可点开，关闭来源返回建议，接受不会丢失原文。
- AI 完成后的待处理建议确实持久化；回到资料和刷新都能继续。
- 不再有效不是删除，有确认说明、数量、展开、恢复、来源；汇总 Wiki 能按对应项目和全部状态打开。
- 人物职位与项目内角色在填写时有明确说明；问题主要在保存后缺少标签。
- 机会明确只记录现实中已发生的投递，不会替用户外发；主任务随阶段变化。
